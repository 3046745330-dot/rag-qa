# 校园知识问答 RAG（带评测闭环）

> **这不是"又一个 RAG demo"。**
> 市面上 99% 的学生 RAG 项目做到"能问答"就停了。
> 这个项目的目标是：**能证明它变好了，而且能说清楚为什么。**

---

## 一、为什么做这个项目

### 你的简历现在的构成

| 项目 | 体现的能力 | 缺口 |
|---|---|---|
| **ai-group**（多模型协作） | 多智能体编排、协议理解、成本控制 | 没有检索能力 |
| **本项目**（RAG + 评测） | 检索、向量、评测体系、数据驱动优化 | —— |

**两者互补**：ai-group 讲"多 Agent 怎么协作"，本项目讲"单个 Agent 怎么把知识用好"。
面试官看到两个项目，会认为你**至少摸过 Agent 的两个核心方向**。

### 真正值钱的地方

我在研究 JD 时发现一个事实：

> **RAG 是出现频率最高的关键词之一，但几乎没人做"能证明它变好了"的 RAG。**

证据：
- 腾讯混元**专门设了"大模型评测算法研究员"岗位**
- Glean 的 JD 写 *"Lead development of scalable evaluation, benchmarking, and optimization loops"*
- 你截图里那个面试官的原话：**"担心 AI 写代码有没有深入理解过每个组件具体逻辑"**

**评测闭环恰恰是回答"深入理解"的最好证据。**
因为你要能评测，就必须先定义"什么叫对"，而定义"什么叫对"需要真正理解检索和生成的每一环。

### 一句话卖点（简历上可以这么写）

> 从零实现校园问答 RAG，**自建 19 题黄金集（含 ground truth 验证）**，
> 用检索命中率 + 答案准确率双指标量化每次改动，
> 并通过对比实验证明混合检索相对朴素向量检索的提升。

**注意加粗那句**——"含 ground truth 验证"的意思是：
每道题的标准答案都被程序检查过"确实存在于源文档中"，不是拍脑袋写的。
这个细节，面试官会注意到。

## 二、技术路线（分 4 个阶段）

```
阶段 1  朴素 RAG —— 建立 baseline
        固定长度切分 → embedding → 向量检索 → 拼上下文 → 生成
        产出：能跑，但精度一般（这就是你要改进的对象）

阶段 2  评测闭环 —— 本项目的灵魂
        黄金集 + 检索命中率 + 答案准确率 + 自动跑分
        产出：一个能一键给出「这次改动是变好还是变坏」的脚本

阶段 3  改进（至少做 2 个）—— 有数据支撑的优化
        · 混合检索（BM25 + 向量）—— 专有名词场景提升明显
        · 重排（Reranker）—— 粗排后的精修
        · 语义切分 —— 替代固定长度切分
        产出：每一步都有「改前 vs 改后」的数字对比

阶段 4  展示 —— 让它能被看见
        极简 Web 界面（能看检索命中了哪几段、分数多少）
        产出：面试时能演示，且能解释每一步
```

> **为什么阶段 2 这么靠前？**
> 因为没有评测就做优化，等于闭着眼睛改代码——你不知道是变好了还是变坏了。
> **这是本项目和你同学的项目最大的区别。**

## 三、评测的两个指标（先定义清楚）

### 指标 1：检索命中率（Retrieval Hit Rate）

```
问题：正确的文档有没有被召回？
算法：top-k 检索结果里，是否包含 source_doc
```

**为什么先测检索而不是直接测答案？**
因为 RAG 的错误有两类，必须分开定位：

| 错误类型 | 表现 | 该改哪里 |
|---|---|---|
| **检索没召回到** | 上下文里根本没有答案 | 改切分 / 改检索算法 |
| **召回了但答错** | 上下文里有，模型没用上 | 改 prompt / 换模型 |

**如果只看最终答案对错，你永远不知道该改哪一环。** 这就是分指标的意義。

### 指标 2：答案准确率（Answer Accuracy）

```
问题：生成的回答里，包不包含关键片段？
算法：golden_set 里的 must_contain 是否都出现在回答里
```

**注意**：这是「规则匹配」不是「LLM 打分」。
为什么？因为规则匹配**确定性**——同样的输入永远同样的结果，可以进 CI。
LLM 打分有随机性，适合做补充，不适合做唯一标准。

> 进阶：后面可以加 **LLM-as-Judge** 做辅助评估，但**规则指标必须是第一层**。

## 四、语料与黄金集（已经为你准备好了）

### 语料：15 个校园文档（3635 字）

```
docs/
├── library-hours.md    图书馆开放时间
├── library-borrow.md   图书借阅规则
├── library-seat.md     图书馆座位预约     ← 和上面两个主题相近
├── lab-hours.md        实验室开放时间     ← 干扰项：也叫"开放时间"
├── gym-hours.md        体育场馆开放时间   ← 干扰项：同上
├── canteen.md          食堂营业信息
├── dorm-power.md       宿舍用电规定
├── network.md          校园网使用指南
├── exam.md             考试与补考规定
├── scholarship.md      奖学金评定
├── card.md             校园卡使用说明
├── medical.md          校医院就诊指南
├── freshman.md         新生入学指南       ← 527 字长文档
├── graduation.md       毕业与学位授予要求  ← 403 字长文档
└── safety.md           校园安全须知         ← 没被考到，纯干扰项
```

**这些语料是故意设计过的**——不是随便找的文档：

- **三个文档都叫"XX开放时间"** → 考验检索能不能区分
- **两个长文档信息埋在中间** → 考验切分策略
- **一个文档完全没被考到** → 纯干扰，考验检索的精确性

### 黄金集：19 道题（已用程序验证）

| 类型 | 题数 | 考察什么 |
|---|---|---|
| `easy` | 5 | 基础能力，应该能过 |
| `trap` | 5 | **有相似文档干扰**，考验区分能力 |
| `buried` | 5 | **答案藏在长文档中间**，考验切分 |
| `multi` | 4 | **答案含多个要点**，考验召回完整性 |

**每道题的 `must_contain` 都已被程序验证「确实存在于源文档中」**（见 `_build_golden_set.py`）。
如果标准答案写错，脚本会拒绝导出黄金集。

## 五、成本预算（重要）

你毕设的 API 预算是 100 元。这个项目的实际成本：

| 操作 | 单价 | 一次评测 |
|---|---|---|
| Embedding（智谱 `embedding-3`） | 极低 | 15 个文档 ≈ **0.003 元** |
| 生成（智谱 `glm-4-air`） | 低 | 19 题 × ≈0.0006 元 ≈ **0.012 元** |
| **跑一轮完整评测** | | **≈ 0.015 元** |

**跑 100 轮评测也才 1.5 元。** 所以你可以放心大胆地反复测——这正是评测闭环能成立的前提。

> 对比：如果用最贵的模型，跑一轮可能就要几块钱，「多测几轮」就变成奢侈了。
> **这也是一个设计决策**：选用便宜模型的目的是让「高频评测」在经济上可行。

## 八、和毕设的关系

**这个项目就是毕设的 RAG 模块原型。**

毕设的后端有一个 RAG 组件（检索校园知识）。本项目把它单独拎出来，
配上完整的评测体系——这样你有两个好处：

1. **毕设的 RAG 部分有了质量保证**（不是"能跑就行"）
2. **简历上多一个能讲深 40 分钟的项目**

**一份努力，两个产出。**
