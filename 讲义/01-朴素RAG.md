# 第 01 课：从零实现一个朴素的 RAG

> **目标：先做一个"能跑但不够好"的 RAG。**
> 为什么先做不好的？因为没有 baseline，你后面所有的优化都无法证明有效。
>
> 这一课结束时你会有：能跑通的 RAG + 一个会显示"命中率 63%"的评测结果。
> **那个 63% 就是你的起跑线，也是你后面要打败的对象。**

---

## 一、RAG 到底在解决什么问题

### 先看它不解决就会怎样

你问模型："我们学校图书馆周末几点开门？"

**不用 RAG**，模型会：
- 如果它训练数据里没有你们学校 → **编一个看起来合理的时间**（幻觉）
- 即使有 —— 训练数据是去年的，你们学校今年改时间了 → **答错且自信**

**核心矛盾**：
```
模型的参数里冻结了「训练那一刻」的知识
但你需要的是「此时此刻、你这个场景」的知识
```

### RAG 的思路

**不改模型，改输入。**

```
不问：  "我们学校图书馆周末几点开门？"
而问：  "根据以下资料回答问题：
         【资料开始】图书馆开放时间安排：周六至周日 09:00-21:00 ...【资料结束】
         问题：我们学校图书馆周末几点开门？"
```

就这么简单。**RAG 不是训练，是"每次问之前，先把相关资料塞进 prompt"。**

### 但"塞"这件事有三个难点

| 难点 | 问题 | 本项目对应 |
|---|---|---|
| **挑哪些塞** | 资料库有 1 万篇，不可能全塞（超上下文、还贵） | 检索 |
| **怎么切** | 一篇 10 页的文档，切多大一块？ | 切分（chunking） |
| **塞多少** | top-3 还是 top-10？多了噪声大，少了漏信息 | top-k 调参 |

**这一课解决"最小可用版本"，后面几课逐个改进。**

---

## 二、RAG 的五个环节

```
① 切分（Chunking）
   长文档 → 切成小块
   ↓
② 向量化（Embedding）
   每块文本 → 一串数字（向量）
   ↓
③ 检索（Retrieval）
   问题也变成向量 → 找最相似的 k 块
   ↓
④ 组装上下文（Context Assembly）
   把 k 块拼成一段文本，塞进 prompt
   ↓
⑤ 生成（Generation）
   把 prompt 发给模型 → 得到答案
```

**这一课你要写全部五个环节。** 看起来很吓人，其实每步都只有十几行代码。

---

## 三、逐环节讲解

### ① 切分：为什么不能整篇塞

假设一篇文档 5000 字，你整篇塞进 prompt。问题：

1. **噪声大** —— 你问"军训多久"，但那一整篇讲的是入学所有事项（报到、体检、选课、军训、户口），相关信息只占 5%。模型容易抓不住重点。
2. **超上下文** —— 文档多了塞不下。
3. **召回不准** —— 检索的单位是"向量"，整篇文档的向量是"平均语义"，问句很难匹配到。

**所以切成小块。** 这一课用最简单的策略：

```
固定长度切分：每 200 字一块，块之间重叠 50 字
```

**为什么要重叠？** 因为纯固定切分会在语义中间切断。比如：

```
...军训安排在开学后第二周，为期|两周。需自备运动鞋...
                                   ↑ 硬切在这里
```

第一块结尾是"为期"，第二块开头是"两周"。**你检索"军训多久"时，两块都不完整。**
重叠 50 字能缓解这个问题（让关键信息至少在某一块里完整出现）。

> **这就是本课要暴露的第一个弱点。** 后面第 03 课会用「语义切分」改进它。
> 但**现在先用笨办法**——不然你没有 baseline。

### ② 向量化：文本怎么变成数字

Embedding 模型把一段文本映射成一个高维向量（本项目用智谱 `embedding-3`，**2048 维**）。

关键词：**语义相近的文本，向量距离近。**

```
"图书馆几点开门"     → [0.012, -0.034, 0.088, ...]  ┐
"图书馆开放时间"     → [0.011, -0.030, 0.091, ...]  ├ 距离近
"食堂几点开门"       → [-0.045, 0.022, -0.013, ...] ┘ 距离远
```

**注意：这是"语义"相似，不是"字面"相似。**
即使两句话没有一个字相同（"闭馆时间" vs "几点关门"），向量也可能很近。

> ⚠️ 但**不是万能的**。专有名词、缩写、型号号这类"字面重要"的场景，
> 纯向量检索经常失手——这**正是第 03 课要引入 BM25 的原因**。
> 你先记住这个伏笔。

### ③ 检索：怎么算"最相似"

用**余弦相似度**（cosine similarity）：

```
similarity = (A · B) / (|A| × |B|)
```

- `A · B` 是点积（对应位置相乘再求和）
- `|A|` 是向量的模长（各元素平方和的平方根）
- 结果范围 `[-1, 1]`，**越接近 1 越相似**

**为什么用余弦而不是欧氏距离？**
因为余弦只看**方向**，不看**长度**。文本长度不同会导致向量模长不同，
但我们关心的是"语义方向"是否一致，不是"向量有多长"。

> 实操提示：如果你的向量已经归一化（模长为 1），
> 那么余弦相似度 **就等于** 点积，可以省一次除法。

### ④ 组装上下文：一个容易忽略的细节

把检索到的块拼起来时，**要带上来源标识**：

```
【片段 1｜来源：library-hours.md】
图书馆开放时间安排如下：周一至周五 08:00-22:00 ...

【片段 2｜来源：library-seat.md】
图书馆自习座位需提前预约 ...
```

**为什么带来源？** 两个原因：
1. 让模型知道不同片段来自不同文档，不要说混
2. **方便调试** —— 答案错了你能立刻看出是检索错了还是生成错了

### ⑤ 生成：prompt 怎么写很关键

```python
SYSTEM = """你是校园问答助手。请严格根据提供的资料回答问题。

规则：
1. 只使用资料中的信息，不要编造
2. 如果资料中找不到答案，明确回答"资料中没有相关信息"
3. 回答要简洁，直接给结论
"""
```

**第 2 条最容易被忽略，但它非常重要。**

如果不写"找不到就说找不到"，模型遇到资料里没有的问题时，
会**顺着资料的语气编一个答案**。这在评测里会表现为"答案看起来对但实际错"。
